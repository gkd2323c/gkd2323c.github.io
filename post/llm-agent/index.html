别让 LLM 同时维护多个心智模型：Agent 工具设计原则

别让 LLM 同时维护多个心智模型：Agent 工具设计原则

引子

最近给 OpenHanako 提了 issue #1495。问题不复杂：Windows 平台下 bash 工具源码里写得很清楚，找不到 bash 就 fail fast，不降级 PowerShell——但商业打包后实际跑的是 Windows PowerShell 5.1。

为了验证，我跑了三条命令：

$PSVersionTable.PSVersion.ToString()
# → 5.1.20348.2849
Get-Process | Select-Object -First 1 Name,Id
# → 0store-service 4496
echo $BASH_VERSION
# → $BASH_VERSION   （字面量，没展开）

bash 工具跑的不是 bash。这件事本身不意外，我之前就知道。但我盯着 echo $BASH_VERSION 那条返回多看了两秒，忽然意识到更深的问题：LLM 在 agent 里被反复要求同时维护多个心智模型（“这个工具跑什么？什么语法？上次哪条错了？"），而每个额外的心智模型都是隐性 prompt 成本加失败概率的提高。

这篇文章是我对这个观察的系统化论述。先说清楚它不是什么，再说什么是它，最后承认我可能漏掉的几个地方。

我看到的现象

我跑了半年 agent 调试，遇到过一类反复出现的失败模式：LLM 写命令时语法正确、工具选对、参数正确，但就是跑不通。事后看错误信息大多是 “shell 不识别这个语法” 或 “这个命令找不到”。重写一遍命令，换个语法就好了。

学术上 arXiv 2512.07497 的 “How Do LLMs Fail In Agentic Scenarios?” 给这种失败起了个名字：tool-use fragility under cognitive load——LLM 不是不懂任务，是认知带宽被占满了。论文基于 900 个 agentic 执行 trace 的质性分析，识别出 4 种 failure archetype，这一类是其中之一。

Berkeley Function Calling Leaderboard 的数据更直接：工具越多，准确率越低。但要注意——这组数据说的是工具数量与准确率的相关性，不一定是工具异质性的效应。10 个同构工具和 10 个异构工具，准确率下降曲线可能完全不同。我下面会用到这条数据，但只把它当作间接证据用，不当结论。

我自己的工程直觉加上这些学术观察指向同一方向：让 LLM 看到的工具环境尽可能一致。具体什么意思我后面说，先聊一聊 MCP 在做什么。

MCP 在做什么

2024 年 11 月，Anthropic 发布 Model Context Protocol，定位是"USB-C for AI”。到 2025 年中，arXiv 2505.02279 出了综述，把 MCP 跟 ACP、A2A、ANP 并列评估。

MCP 解决的是接口碎片化。在它之前，每个 agent 框架（LangChain、CrewAI、AutoGen）有自己的 tool calling 规范，工具不能跨框架复用。MCP 把这部分统一了。Google Cloud、Oracle、Nebius 的工程 blog 评价都挺高。Anthropic 自己内部也用 MCP 替代 BigQuery CLI，说"maintain better security control"。

但有意思的是 Anthropic 自己并不全走 MCP。Claude Code 有 8+ 个内置工具（Bash、Read、Edit、Grep、Glob、LS），全部 in-process 实现。Claude API 的 Bash、Text Editor、Computer Use 是 schema-less tool，schema 直接 build 到 model 里。只有用户/插件加的工具才走 MCP。

这个取舍最常被解释成"性能关键路径 in-process，扩展生态走 MCP"——延迟敏感所以不绕 MCP server。这个解释对，但只是故事的一面。另一面是信任边界：in-process 工具跑在用户本地机器上，访问本地文件系统和 shell 权限；MCP 工具由第三方提供，运行在隔离的进程里。Anthropic 作为模型提供商和工具实现者的双重身份，让它能把"哪些工具值得放到用户进程里"和"哪些应该隔离"分得比较清楚。第三方平台没这个特权。

我读 Pragmatic Engineer 的 Claude Code 架构分析 和 arXiv 2604.14228 的 Claude Code 源码 leak 分析时，这两层原因都浮现出来，但官方文档通常只讲第一层。

一个真实案例

issue #1495 完整故事如下。

源码 lib/sandbox/win32-exec.js 写得很清楚：

PowerShell 不在候选列表中：PI SDK 生成 bash 语法（&&、管道、command substitution 等），PowerShell 语法完全不兼容，静默降级只会让每条命令以莫名方式失败。如果所有 bash 兼容 shell 都不可用，应该 fail fast 并给出明确的安装指引。

但商业打包的 resources/server/bundle/index.js（minified）实际跑的是 Windows PowerShell 5.1。源码设计的"不降级 PowerShell"被静默绕过了。

先承认一点：这个 bug 严格来说是构建完整性问题，不是设计哲学问题——minify 后的 bundle 没有正确执行源码的 fail-fast 逻辑。如果打包 pipeline 加了严格校验，#1495 根本不会出现。我用它作为引子是触发，不是证明。后面会讲到这条原则在哪些场景根本不适用。

临时绕开方案倒是意外地干净——mcp_windows-mcp_PowerShell 工具是独立于 Hanako 平台的 MCP server，实测跑的是 PowerShell 7.6.2，不是被劫持的 PS 5.1。绕开被劫持的 bash 工具再 spawn 平台自带的 PortableGit，能拿到真 MINGW64 bash：

& 'C:\Program Files\Hanako\resources\git\bin\bash.exe' -c "echo hello; uname -a"
# → MINGW64_NT-10.0-20348 ... Msys

讽刺的是这个绕开方案恰好就是「统一接口」原则的实践——MCP 工具的描述明确写"PowerShell commands"，LLM 一看就知道写什么语法，认知负担归零。

一条原则

把上面的观察压成可操作的判断标准：

「这会让 LLM 多维护一个心智模型吗？」是则反对。

应用起来很直接。

加一个新工具，描述清楚 runtime——LLM 心智模型没增加，通过。让一个工具支持多 shell runtime，配置项切换——LLM 每次调用要决定一个，否决。给 prompt 加 shell-specific 警告——本质上是在补救一个不该存在的问题，否决；应该去修问题本身而不是堆 prompt。

这条原则的好处是可执行。架构上有争议时问这条，多数情况下答案就出来了。

这条原则在哪不成立

写完回头看才发现，前面漏了几件事。补上：

第一，平台本身不是单态的时候。 「单态化」能成立的前提是平台本身就是单态的。一个同时支持 Windows、macOS、Linux 的平台，没法在 shell 层面做到真正的单态，除非它在所有 OS 上强制捆绑同一个 shell——而这本身就是另一种环境不一致（你把一个 Unix 兼容层塞进 Windows 里，那个 bash 能碰到的文件系统、环境变量、权限模型和 Linux 上的 bash 也不是同一个东西）。我之前没明说适用范围：这条原则主要适用于单 OS、单一部署场景的平台。跨平台部署需要别的设计。

第二，迁移过渡期。 从 bash 迁到 pwsh 的过程中，LLM 必然同时面对两种工具——旧工具还没退役，新工具还没覆盖全部功能。严格按这条原则，迁移根本无法启动。这条原则是稳态设计的判断标准，不是动态演进的指导原则。

第三，多 LLM provider 协作。 不同的 LLM 训练分布不同。Claude 可能对 bash 更友好（Anthropic 的 Unix 基因），Gemini 可能对 PowerShell 更友好（Microsoft-Google 合作生态）。如果强制单 shell 而那个 shell 恰好是某个 provider 的弱项，相当于在单态化的名义下主动降低了那个 provider 的工具调用质量。

第四，反方更彻底的方案是动态适配。 autoconf 那一类工具的哲学是：构建时检测环境，运行时透明处理差异。LLM 不需要维护多个心智模型，因为平台在底层就把差异消化了。统一翻译是这条思路的 LLM 视角版本——我之前把它放在 fallback 而不是主路径，但客观讲这条思路可能比单态化更通用。代价是翻译层是新的 bug 源。

第五，#1495 证明的不是单态化本身。 它证明的是构建完整性校验的缺失。如果平台严格执行源码设计意图（fail fast 而不是降级），LLM 至少能拿到一个清晰的错误信息（“no bash found”），而不是被偷偷降级到 PowerShell。好的失败模式比坏的伪成功有用。

第六，“心智模型"这个说法本身可疑。 LLM 没有工作记忆——它每次调工具时的上下文是一次性的 token 序列输入输出。它不会"记得"上次的错误是因为 shell 不匹配，除非那次错误信息被写回了 context window。我用"心智模型"是拟人化人类工程师的认知过程，可能不严格成立。换成更精确的说法：让 LLM 看到的工具行为预期保持一致，减少它需要"在每次调用时重新做匹配"的次数。意思接近，但少了拟人化的过度承诺。

接下来

我打算把这条原则应用到我自己的两个项目里。一个是 Hanako 平台的 plugin 工具集，按"工具描述明确 runtime + 平台核心工具 in-process 但行为可预测"过一遍。另一个是 Skyrim 模组管理工具——虽然和 agent 没关系，但里面调用 subprocess 的部分同样适用（mod 安装脚本在不同 shell 下行为不同，强迫用户记两种语法是浪费）。

如果这条原则对你也有用，欢迎讨论。具体的反例、边界情况、或者你踩过的别的"心智模型爆炸"案例，都可以发到 issue #1495 下面一起看。我前面列的 5 个不成立场景大概率不完整，欢迎补全。
