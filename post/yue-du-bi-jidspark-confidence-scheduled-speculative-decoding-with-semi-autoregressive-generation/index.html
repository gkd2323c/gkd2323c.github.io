  • arXiv：2607.05147v1
  • 发布时间：2026-07-06
  • 主类目：cs.AI，另含 cs.CL
  • 主题：大模型推理加速、speculative decoding、半自回归草稿模型、系统感知调度、生产 serving
  • 一句话概括：DSpark 把 speculative decoding 从“每个请求尽量多猜几个 token”换成“看全系统负载，只验证划算的草稿前缀”。

1. 论文要解决的问题

大模型自回归生成，每吐一个 token 就要目标模型跑一次 forward。输出越长延迟越高，decode 阶段 GPU 还经常吃不饱。

Speculative decoding 的思路很朴素：先让一个便宜的 draft model 猜一段候选 token，再由完整 target model 一次并行验证。配合拒绝采样，它能在不改变目标模型输出分布的前提下，砍掉目标模型的调用次数。

论文说，这套东西搬到生产环境会撞上两个瓶颈。

1.1 草稿质量瓶颈

并行 drafter 一次能吐好几个 draft token，快，但位置之间没有真实依赖。要是上下文同时容得下几种续写，比如：

  • “of course”
  • “no problem”

并行模型会在各个位置各自对所有路径取平均，拼出 “of problem”“no course” 这种前言不搭后语的组合。论文管这叫 multi-modal collision。后果是越往后的 draft token 越容易被目标模型拒掉，也就是 suffix acceptance decay。

1.2 系统吞吐瓶颈

drafter 能吐出很长的候选块，不等于这些 token 都值得送去验证。

低并发时多验几个 token 无所谓。高并发就不一样了：每多验一个大概率要被拒的 token，都在占目标模型的 batch capacity，把其他活跃请求挤出去。验证预算于是从单请求的贪心，变成一个系统级的资源分配问题。真正要回答的是，在当前请求分布和系统负载下，每个请求该验证几个 draft token。

这个长度显然不能是常数，得同时看请求难度、draft 置信度，还有 serving 引擎此刻的负载。

2. DSpark 的核心设计

DSpark 有两个主要组件：

  1. Semi-Autoregressive Generation：用半自回归结构改善并行 drafter 的后缀质量。
  2. Confidence-Scheduled Verification：用置信度和硬件吞吐曲线动态选择验证前缀长度。

2.1 半自回归生成：并行 backbone 加轻量顺序头

DSpark 的 drafter 分成两段。

并行阶段

并行 backbone 类似 DFlash，一次 forward 处理整个 draft block，吐出每个位置的 hidden state 和 base logits。并行 drafter 的好处它保留了：draft 成本不随 block 长度线性增长。

顺序阶段

采样 draft token 时，DSpark 从左到右引入轻量级 transition bias，让当前位置能依赖已经采样出的前缀 token。

论文给出两种实现。

Markov head

Markov head 只依赖前一个 token。它可以理解成一个低秩转移矩阵。

上一个 token 是 “of” 时，它能抬高 “course” 的分数，压低 “problem”，缓解并行生成里的路径混合。

这是论文默认用的方案，因为它简单、部署友好，收益又已经很明显。

RNN head

RNN head 维护一个 recurrent state，能利用更长的 block 内前缀历史，表达能力更强。但论文实验显示，它相比 Markov head 的额外收益主要出现在更长的 draft block 上，整体有限，部署却更复杂。所以生产还是用 Markov head。

2.2 置信度调度验证：验证“值得验证”的 token

DSpark 为每个 draft 位置预测一个置信度。

它表示：在前面 token 都已被接受的条件下，第 (k) 个 draft token 能通过 target verification 的概率。

一个长度为 (j) 的前缀全部存活的概率是累计乘积。

调度器将所有请求的候选前缀扩展按累计存活概率排序，并结合预先 profile 得到的引擎吞吐曲线。

其中 (B) 是目标模型一次验证的 token batch size，SPS 表示 steps per second。

3. “无损”约束与因果性问题

Speculative decoding 的吸引力在于它可以保持目标模型输出分布不变。但这个性质依赖一个关键条件：调度决策不能偷看未来 token。

论文称之为 non-anticipating property。如果第一个 draft token 是否被送去验证，取决于这个 token 实际采样出来是什么，那么输出分布会被选择机制污染。

论文附录 A 给出反例：

  • draft 第一个位置可能采样出 A 或 B；
  • 如果采到 A，后续 confidence 高，调度器决定验证；
  • 如果采到 B，后续 confidence 低，调度器决定不验证；
  • 结果 A 更容易进入最终输出，导致输出分布偏离 target model。

因此理论算法中用 early stopping，不拿未来候选 token 的信息去影响当前的 admission decision。

生产实现里情况更麻烦。DeepSeek serving 系统有 Zero-Overhead Scheduling 和 CUDA graph replay 这些约束，论文改用异步调度：用两步前的历史预测决定动态容量 (K)，当前候选 token 仍按实时 confidence 排序进入 top-K。作者认为这形成了一道因果隔离屏障，既能适配真实硬件中不平滑的吞吐曲线，也能维持目标分布的精确性。

这一点最值得盯：理论调度器和生产调度器并不一样，生产版的正确性吊在“异步历史信息不泄露当前 token realization”这个前提上。

4. 训练目标

DSpark 训练时冻结 target model，只训练 draft backbone、sequential head 和 confidence head，并共享目标模型的 embedding layer 与 LM head。

训练目标包括三项。

4.1 交叉熵损失

让 drafter 预测真实 token

4.2 分布匹配损失

约束 draft distribution 接近 target distribution

这项损失有直接动机：speculative decoding 的单步接受率与总变差距离相关。

降低总变差距离，等价于提高预期接受率。

4.3 置信度损失

训练 confidence head 预测 soft acceptance label

三项损失按权重合并

另外，论文对前面位置使用更高权重，因为 speculative decoding 接受的是连续前缀，前面的 token 更关键。

5. 离线实验

5.1 实验设置

目标模型包括：

  • Qwen3-4B
  • Qwen3-8B
  • Qwen3-14B
  • Gemma4-12B

对比 drafter：

  • Eagle3：自回归 drafter
  • DFlash：并行 drafter
  • DSpark：本文方法

任务域包括：

  • 数学：GSM8K、MATH500、AIME25
  • 代码：MBPP、HumanEval、Live-CodeBench
  • 聊天：MT-Bench、Alpaca、Arena-Hard

主要指标是每轮 speculative decoding 的 accepted length (\tau)，越高越好。论文说明该指标包含 target-generated bonus token。

5.2 主要结果

论文报告，在 Qwen3-4B、8B、14B 上，DSpark 相比 Eagle3 的 macro-average accepted length 分别提升：

  • 30.9%
  • 26.7%
  • 30.0%

相比 DFlash 分别提升：

  • 16.3%
  • 18.4%
  • 18.3%

在 Gemma4-12B 上也有一致收益。

一个重要现象是：结构化任务的 accepted length 显著高于开放聊天。以 Qwen3-4B 上的 DSpark 为例：

  • 数学任务平均接受长度更高；
  • 代码任务也较高；
  • 聊天任务较低。

这说明静态验证长度不是好选择。代码和数学可以多验，开放聊天里盲验长后缀就是在浪费目标模型容量。

6. 关键分析实验

6.1 为什么并行 drafter 能超过自回归 drafter

直觉上，自回归 drafter 应该更准，因为它能利用前缀 token。但论文发现，Eagle3 这类自回归 drafter 受顺序延迟限制，结构往往较浅；DFlash 和 DSpark 这样的并行 drafter 可以使用更深的网络。

结果是：

  • 第一个 draft token 上，并行模型容量更强，准确率更高；
  • speculative decoding 又极度依赖第一个 token，因为第一个 token 被拒绝会使后续草稿全部失效；
  • 因此并行模型虽然后缀衰减快，整体 accepted length 仍可能超过浅层自回归 drafter。

DSpark 的设计恰好把两边合起来：并行 backbone 提供第一个 token 的高容量预测，轻量 sequential head 修后续 token 的条件依赖。

6.2 Markov head 的性价比

论文发现 2-layer DSpark 就能超过 5-layer DFlash。这说明给并行 drafter 加入局部自回归依赖，比单纯堆更深的并行层更有效。

当 proposal length 增加时，DSpark 相对 DFlash 的优势变大：

  • (\gamma=7)：数学 +16%，代码 +15%，聊天 +18%；
  • (\gamma=15)：数学 +30%，代码 +26%，聊天 +22%。

顺序采样带来的延迟开销很小。论文报告在 batch size 128 下，draft length 从 4 扩展到 16，相比 DFlash 的整轮延迟只增加 0.2% 到 1.3%，但 accepted length 最高可提升约 30%。

6.3 Confidence head 与校准

论文通过 threshold sweep 证明，confidence head 能识别低价值后缀。随着 threshold 提高，验证 token 减少，但整体 acceptance rate 上升。

聊天任务中，acceptance rate 从 45.7% 提升到 95.7%。数学和代码也提升：

  • 数学：76.9% → 92.5%
  • 代码：67.6% → 92.0%

但 raw confidence 存在过度自信问题。论文报告其 ROC-AUC 为 0.81 到 0.90，排序能力较好，但 ECE 为 3% 到 8%。通过 Sequential Temperature Scaling 校准后，平均 ECE 降至约 1%。

这个区别影响不小，因为调度器不只靠排序，还要置信度的绝对数值来估计期望吞吐。

7. 生产部署结果

论文将 DSpark 部署到 DeepSeek-V4-Flash preview 和 DeepSeek-V4-Pro preview 的生产 serving 系统中，对比原生产 baseline MTP-1。生产版本使用 DSpark-5，最大 draft length (\gamma=5)。

7.1 V4-Flash

  • 在 80 tok/s/user SLA 下，DSpark 的 aggregate throughput 比 MTP-1 高 51%。
  • 在 120 tok/s/user 严格 SLA 下，DSpark 的 nominal aggregate throughput 高 661%。
  • 在 matched practical throughput levels 下，DSpark 的 per-user generation speed 提升 60% 到 85%。

7.2 V4-Pro

  • 在 35 tok/s/user SLA 下，aggregate throughput 提升 52%。
  • 在 50 tok/s/user 严格 SLA 下，nominal throughput 高 406%。
  • 在 matched system capacity 下，per-user generation speed 提升 57% 到 78%。

7.3 对大数字的解释

论文自己对 661% 和 406% 的解释比较克制：这些高倍数主要来自 MTP-1 在严格 SLA 下进入低并发退化区，不能将其理解为一般场景下稳定数倍加速。

更稳妥的结论是：

  • 中等 SLA 下，DSpark 带来约 51% / 52% aggregate throughput 提升；
  • 同等吞吐水平下，DSpark 带来 57% 到 85% 的单用户生成速度提升；
  • 严格 SLA 下，DSpark 能维持 MTP-1 几乎撑不住的交互档位。

8. 论文贡献

8.1 算法结构贡献

DSpark 提出一种半自回归 drafter：并行 backbone 负责高容量快速预测，轻量 sequential head 负责补足 block 内局部依赖。它在保持 drafting 速度的同时缓解了并行生成的 suffix decay。

8.2 调度机制贡献

论文将 verification length selection 形式化为系统吞吐优化问题，而不是固定长度或固定阈值策略。它显式考虑：

  • draft token 的累计存活概率；
  • 当前 batch 中多个请求之间的资源竞争；
  • 硬件吞吐曲线 (SPS(B))。

8.3 生产系统贡献

这篇论文的系统部分很重。它处理了真实部署中的几个难题：

  • 硬件吞吐曲线离散且不平滑；
  • Zero-Overhead Scheduling 需要提前知道下一步 batch size；
  • variable-length verification 会破坏标准 fixed-query-length kernel 的效率；
  • 动态调度必须保持 speculative decoding 的无损分布性质。

这些内容让 DSpark 更像一次模型结构、训练目标、调度策略和 serving kernel 的联合优化，而不只是一个离线 accepted length 改进。

9. 局限与疑点

9.1 外部复现难度高

论文开源了 DSpark checkpoints 和 DeepSpec，但生产结果依赖 DeepSeek 内部 serving stack、HAI-LLM、ZOS、定制 sparse attention / compress kernels 和真实用户流量。外部团队更容易复现离线 accepted length，很难复现线上吞吐边界。

9.2 基础设施绑定强

硬件感知 scheduler 需要预先 profile 引擎吞吐曲线，并要求推理框架支持动态 verification batch。普通 vLLM、TensorRT-LLM 或自研 serving 系统要迁移完整方案，成本不会低。

9.3 fixed draft cost 仍然存在

DSpark 仍要先生成完整 draft block。对于复杂、开放、低接受率请求，这部分 draft compute 可能无法回收。论文也承认，未来可以加入 difficulty-aware early exiting，让难请求提前绕过完整 draft generation。

9.4 生产无损性需要实现级验证

理论部分对 non-anticipating property 的说明很清楚。生产部分通过两步前历史预测形成因果屏障，这个论证在概念上合理，但外部读者无法直接审计实现细节。对于无损采样系统，任何 admission decision 的因果边界都很敏感。

9.5 严格 SLA 提升数字容易被误用

661% / 406% 不是常规稳定加速倍数，而是 baseline 在严格 SLA 下退化后形成的相对优势。引用这两个数字时必须附带解释，否则容易夸大论文结论。

10. 与相关路线的关系

DSpark 位于 speculative decoding 的系统化方向上。它和以下路线相关：

  • multi-token prediction / MTP；
  • Medusa、Eagle、DFlash 等 drafter 结构；
  • rejection sampling 保持目标分布的 speculative decoding；
  • serving 系统中的 goodput / latency / batch capacity 调度。

它的核心变化是把问题从单请求层面的“能多猜几个 token”转为系统层面的“哪些 token 值得消耗目标模型 batch capacity 去验证”。

这对生产推理系统很关键，因为线上瓶颈常常不是 draft model 能不能提出候选，而是目标模型验证预算在高并发下是否被浪费。

11. 个人判断

这是一篇工程价值很高、系统意识很强的 speculative decoding 论文。

它最值钱的不是某个单独公式，而是三件事咖到一起：

  1. 用半自回归 head 修并行草稿的后缀崩塌；
  2. 用 confidence 和 calibration 把“会不会被接受”变成可调度信号；
  3. 用硬件吞吐曲线和实时负载决定验证预算。

如果关心的是怎么让大模型服务真正更快，这篇比很多只报离线 accepted length 的论文更值得读。它直接碰了高并发生产场景里的批容量竞争、SLA 约束和动态调度。

但它不是一个能即插即用的通用技巧。DSpark 很大程度上是 DeepSeek 对自家生产 serving 栈的一次深度联合优化。外部团队借鉴时，最该先吸收的是一个前提：speculative decoding 的瓶颈不只是 draft 准不准，还包括验证预算在全局 batch capacity 中划不划算。

12. 后续可追的问题

  1. DSpark 在 vLLM / TensorRT-LLM 等公开 serving 框架中能否保持类似收益？
  2. 两步前历史预测形成的 causal barrier，是否有形式化证明或更细粒度实现审计？
  3. 对低接受率请求，difficulty-aware early exit 能减少多少固定 draft cost？
  4. Markov head 对不同语言、代码、数学符号序列的迁移能力是否一致？
  5. 如果目标模型进入 thinking mode，draft acceptance 和 confidence calibration 会如何变化？
  6. DSpark 与 tree-based speculative decoding 是否能结合，还是系统复杂度会抵消收益？

13. 可引用结论

  • DSpark 的本质是把 speculative decoding 从“每个请求尽量多猜”改成“全系统只验证期望收益为正的草稿前缀”。
  • 半自回归 head 用很小的顺序成本换来了显著的后缀一致性收益。
  • 生产环境中的 speculative decoding 是调度问题，不只是模型结构问题。
  • 严格 SLA 下的 661% / 406% 应理解为交互档位扩展，而非一般场景稳定数倍加速。
  • 对外复现时，离线 accepted length 较容易验证，线上 Pareto frontier 依赖 DeepSeek 内部 serving 栈，复现难度高。
